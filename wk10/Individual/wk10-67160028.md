## โจทย์ที่ 1: วิเคราะห์การออกแบบ Input Form เทียบกับหลักการ

**หน้าจอที่เลือกวิเคราะห์:** **ฟอร์มรับออเดอร์หน้าร้าน (POS Order Form)**  
_(อ้างอิงหน้าจอจาก Workshop สัปดาห์ที่ 10 และตัวอย่างใน week10.pdf หัวข้อ 1.4 และ 3.5)_

การวิเคราะห์เปรียบเทียบฟอร์มจริงของกลุ่มกับหลักการออกแบบ Input Form 4 ข้อในหัวข้อ 1.2 ของ `wk10.md`:

### 1. Field Type ที่เหมาะสม (Appropriate Field Type)

- **การปฏิบัติตามหลักการ:** **ผ่านเกณฑ์ (Pass)**
- **การวิเคราะห์ฟอร์มจริง:** ฟอร์มเลือกใช้ชนิดของ Input Component ได้เหมาะสมกับลักษณะข้อมูล:
  - การเลือกเมนูเครื่องดื่มใช้ **Dropdown / Menu Button Cards** แทนการให้พนักงานพิมพ์ข้อความอิสระ (Free Text) ช่วยลดความผิดพลาดในการสะกดชื่อเมนูและป้องกันการเลือกเมนูที่ไม่มีอยู่จริง
  - ช่องจำนวนสินค้า (Quantity) ใช้ **ปุ่มปรับจำนวน (Stepper Controls `[-] [ 1 ] [+]`)** ร่วมกับ Number Input เพื่อจำกัดให้กรอกได้เฉพาะตัวเลข
  - การเลือกวิธีชำระเงินใช้ **Radio Buttons / Payment Option Cards** (`เงินสด` / `QR Code`) ซึ่งตรงกับข้อมูลที่มีตัวเลือกจำกัดและเลือกได้เพียงตัวเลือกเดียว
- **ข้อสรุป:** ปฏิบัติตามหลักการ Recognition Rather Than Recall และ Error Prevention ได้อย่างสมบูรณ์

---

### 2. Validation การตรวจสอบความถูกต้อง (Client & Server Validation)

- **การปฏิบัติตามหลักการ:** **ยังไม่ครบถ้วน / มีจุดบกพร่อง (Incomplete / Needs Improvement)**
- **การวิเคราะห์ฟอร์มจริง:**
  - _จุดที่ผ่าน:_ มี Server-side validation ใน Backend Controller ตาม Sprint 2 (ตรวจสอบ `items`, `branchId`, `employeeId`, `paymentMethod` และชนิดตัวเลข)
  - _จุดที่ยังขาด:_ ฝั่ง Client-side UI ยังขาดการตรวจสอบเชิงป้องกัน (Defense in Depth) 2 จุดสำคัญ:
    1. **ปุ่ม "ยืนยันการสั่งซื้อ (Confirm Order)" ยังไม่ได้ถูก Disable เมื่อตะกร้าสินค้าว่างเปล่า:** ในสถานะเริ่มต้นที่ยังไม่มีสินค้าในตะกร้า (`cartItems.length === 0`) พนักงานยังคงกดปุ่มยืนยันได้ ทำให้ส่ง HTTP Request ไปยัง Server โดยไม่จำเป็น และต้องรอ Server ตอบกลับ 400 Bad Request
    2. **ยังขาดการจำกัดจำนวนรายการสินค้าสูงสุด 20 รายการบนหน้าจอ:** ตาม Business Rule ของ Sprint 2 ที่จำกัดรายการสินค้าไม่เกิน 20 รายการต่อออเดอร์ (`items.length <= 20`) หน้าจอ POS ของกลุ่มยังไม่มี Client Validation ดักจับเมื่อพนักงานกดเพิ่มรายการเกิน 20 รายการ
- **ข้อเสนอแนะในการแก้ไขที่นำไปปฏิบัติได้จริง:**
  - เพิ่ม Client-side Event Handler เพื่อควบคุมสถานะปุ่มยืนยัน:
    ```javascript
    // ปิดการใช้งานปุ่มยืนยันหากไม่มีสินค้าในตะกร้า หรือยังไม่เลือกวิธีชำระเงิน
    confirmButton.disabled = cartItems.length === 0 || !selectedPaymentMethod;
    ```
  - เพิ่มเงื่อนไขตรวจสอบก่อนเพิ่มรายการสินค้าลงตะกร้า: หากรายการสินค้าในตะกร้ามีครบ 20 รายการแล้ว ให้ Disable ปุ่ม "+ ปุ่มเพิ่มรายการ" พร้อมแสดงข้อความเตือนว่า _"รายการสินค้าต่อออเดอร์ครบขีดจำกัด 20 รายการแล้ว"_

### 3. Default Value ค่าเริ่มต้น (Sensible Default Values)

- **การปฏิบัติตามหลักการ:** **ผ่านเกณฑ์ (Pass)**
- **การวิเคราะห์ฟอร์มจริง:** ฟอร์มมีการกำหนดค่าเริ่มต้นที่สอดคล้องกับพฤติกรรมการใช้งานจริงของร้านกาแฟ:
  - ช่องระบุจำนวนสินค้าถูกกำหนดค่าเริ่มต้นเป็น **`1`** อัตโนมัติทันทีที่พนักงานคลิกเลือกเมนู (แทนที่จะปล่อยให้เป็นช่องว่างหรือ 0) เนื่องจากลูกค้าส่วนใหญ่สั่งเครื่องดื่มอย่างน้อย 1 แก้ว ช่วยลดภาระการกดป้อนตัวเลขของพนักงาน
  - สำหรับวิธีชำระเงิน ทางกลุ่มตัดสินใจ **ไม่ตั้งค่าเริ่มต้น (Default)** ให้กับเงินสดหรือ QR Code เพื่อบังคับให้พนักงานต้องถามและเลือกตามความต้องการจริงของลูกค้า ป้องกันการกดยืนยันผิดประเภท
- **ข้อสรุป:** ปฏิบัติตามหลักการช่วยลดภาระการกรอกข้อมูล (Cognitive Load Reduction) ได้เป็นอย่างดี

---

### 4. Immediate Feedback การแจ้งเตือนทันที (Visibility of System Status)

- **การปฏิบัติตามหลักการ:** **ยังไม่ครบถ้วน / มีจุดบกพร่อง (Incomplete / Needs Improvement)**
- **การวิเคราะห์ฟอร์มจริง:**
  - _จุดที่ผ่าน:_ เมื่อเลือกเมนูที่สินค้าหมด ระบบแสดงข้อความแจ้งเตือนสีแดง _"Temporarily Out of Stock"_ และ Disable ปุ่มเพิ่มรายการทันที
  - _จุดที่ยังขาด:_
    1. **ปุ่มลดจำนวน `[-]` ไม่มีการตอบสนองเมื่อจำนวนอยู่ที่ค่าต่ำสุด (1 หน่วย):** เมื่อตัวเลขจำนวนอยู่ที่ 1 พนักงานยังสามารถกดปุ่ม `[-]` ได้ แม้ระบบจะไม่ลดค่าลงต่ำกว่า 1 แต่ไม่มี Visual Hint หรือการ Disable ปุ่ม `[-]` ทำให้พนักงานเกิดความสับสนว่าระบบค้างหรือไม่
    2. **ยอดรวมราคาสุทธิ (Grand Total) ยังไม่คำนวณแบบ Real-time ทันทีที่มีการแก้ไขจำนวนในตะกร้า:** เมื่อมีการปรับเปลี่ยนจำนวนแก้วในตารางสรุปรายการ ยอดรวมราคาสุทธิด้านล่างยังไม่อัปเดตแบบทันทีทันใด (ต้องรอการ Refresh หรือคำนวณใหม่)
- **ข้อเสนอแนะในการแก้ไขที่นำไปปฏิบัติได้จริง:**
  - ผูกฟังก์ชันตรวจสอบค่าจำนวนเข้ากับปุ่ม `[-]`: เมื่อ `quantity === 1` ให้กำหนด `btnMinus.disabled = true;` และเปิดใช้งานเมื่อ `quantity > 1` เพื่อสื่อสารสถานะของระบบแก่ผู้ใช้ทันที
  - นำ Reactive State Binding มาใช้กับการแก้ไขรายการสินค้าในตะกร้า: เมื่อมีการกดเพิ่ม/ลดจำนวน หรือลบรายการ ให้ฟังก์ชัน `calculateGrandTotal()` ทำงานและอัปเดตตัวเลขยอดรวมสุทธิบนหน้าจอทันทีแบบ Real-time

## โจทย์ที่ 2: วิเคราะห์ประเภทของ Output/Report ที่กลุ่มออกแบบ

**ชิ้นงานที่เลือกวิเคราะห์:** **รายงานสรุปยอดขายประจำวัน (Daily Sales Summary Report)**  
_(อ้างอิงชิ้นงานจาก Workshop สัปดาห์ที่ 10 และตัวอย่างใน week10.pdf หัวข้อ 2.5)_

---

### 2.1 การจัดประเภท Output/Report ตามหลักวิชาการ (หัวข้อ 2.1 และ 2.3)

#### 1. การจำแนกระดับ Output (หัวข้อ 2.1): Output แบบธุรกรรมเดียว vs แบบรายงาน (Report)

- **การจัดประเภท:** จัดเป็น **Output แบบรายงาน (Report)**
- **เหตุผลอิงลักษณะข้อมูลจริงของกลุ่ม:**
  ชิ้นงานนี้ไม่ได้แสดงผลลัพธ์ของคำสั่งซื้อใดคำสั่งซื้อหนึ่งเป็นการเฉพาะ (ซึ่งต่างจาก _ใบเสร็จรับเงิน_ ที่เป็น Output แบบธุรกรรมเดียวเพื่อเป็นหลักฐานแก่ลูกค้า) แต่เป็นการ **รวบรวมข้อมูลจากธุรกรรมจำนวนมาก (Multiple Orders)** ที่เกิดขึ้นตลอดทั้งวันภายในสาขา นำมาประมวลผลสรุปรวมเป็นชุดข้อมูลสถิติ เพื่อให้ผู้บริหารหรือเจ้าของร้านนำไปใช้ในการวิเคราะห์ผลการดำเนินงานและวางแผนธุรกิจ

#### 2. การจำแนกประเภทย่อยของรายงาน (หัวข้อ 2.3)

- **ประเภทหลัก:** **Summary Report (รายงานสรุป)**
  - _เหตุผล:_ ข้อมูลในรายงานถูกประมวลผลโดยการจัดกลุ่มตามเมนูสินค้า (Group by Menu) แสดงเฉพาะข้อมูลเชิงสรุป ได้แก่ จำนวนแก้วที่ขายได้รวม (Qty Sold) และยอดขายรวมสุทธิของแต่ละเมนู (Total Sales) ตลอดจนยอดขายรวมทั้งสิ้น (Grand Total) โดยตัดรายละเอียดของแต่ละธุรกรรมย่อยทิ้งไป (ไม่แสดงเลขที่ใบเสร็จ, เวลาที่ซื้อเป็นรายนาที, หรือพนักงานที่ทำรายการแต่ละใบเหมือนใน Detail Report)
- **มิติเวลาในการเรียกใช้งาน:** **On-demand Report**
  - _เหตุผล:_ เป็นรายงานที่เจ้าของร้านหรือผู้จัดการสามารถกดเรียกดูข้อมูลได้ตามต้องการผ่านระบบ ณ เวลาใดก็ได้ ไม่ใช่รายงานที่ระบบตั้งเวลาส่งอัตโนมัติตามรอบเวลา (Scheduled Report)

---

### 2.2 การวิเคราะห์เทียบกับหลักการออกแบบ Output 3 ข้อ (หัวข้อ 2.2)

### 1. จัดลำดับความสำคัญของข้อมูล (Visual Hierarchy)

- **การปฏิบัติตามหลักการ:** **ผ่านเกณฑ์ (Pass)**
- **การวิเคราะห์ชิ้นงานจริง:** รายงานมีการจัดลำดับสายตา (Visual Hierarchy) ที่ดีตามหลัก Information Design:
  - ส่วนหัวรายงานระบุบริบทชัดเจน: แสดงชื่อรายงาน "รายงานสรุปยอดขายประจำวัน", วันที่ที่ออกรายงาน, และชื่อสาขา
  - ส่วนตารางจัดวางหัวคอลัมน์ชัดเจน อ่านง่าย
  - **แถวยอดรวมทั้งสิ้น (Grand Total):** จัดวางไว้ที่แถวล่างสุดของตาราง พร้อมเน้นด้วย **ตัวหนา (Bold font)** และพื้นหลังแถบสีที่เด่นชัด ทำให้เจ้าของร้านสามารถกวาดสายตามองเห็นตัวเลขยอดขายรวมของวันได้ในทันทีโดยไม่ต้องค้นหา
- **ข้อสรุป:** ผู้ใช้รับรู้ข้อมูลสำคัญที่สุดได้รวดเร็วตามหลัก Visual Hierarchy

---

### 2. ใช้รูปแบบที่เหมาะกับผู้ใช้แต่ละกลุ่ม (Format Suited for Target Audience)

- **การปฏิบัติตามหลักการ:** **ยังไม่ครบถ้วน / มีจุดบกพร่อง (Incomplete / Needs Improvement)**
- **การวิเคราะห์ชิ้นงานจริง:**
  - _จุดที่ผ่าน:_ ผู้ใช้เป้าหมายคือเจ้าของร้าน/ผู้จัดการ ซึ่งต้องการตัวเลขสรุปผลประกอบการมากกว่ารายละเอียดปลีกย่อย การนำเสนอในรูปแบบตารางสรุปจึงตรงกับความต้องการพื้นฐาน
  - _จุดที่ยังขาด:_ รายงานของกลุ่มนำเสนอเฉพาะ **ตารางตัวเลขแบบคงที่ (Static Table)** เพียงอย่างเดียว ขาดการนำเสนอเชิงภาพ (Data Visualization) สำหรับผู้บริหารที่ต้องการวิเคราะห์แนวโน้มและตัดสินใจเชิงกลยุทธ์ (เช่น การสั่งซื้อวัตถุดิบหรือการจัดโปรโมชัน) การดูเฉพาะตัวเลขในตารางทำให้มองไม่เห็นสัดส่วนเมนูขายดีหรือแนวโน้มได้อย่างรวดเร็ว
- **ข้อเสนอแนะในการแก้ไขที่นำไปปฏิบัติได้จริง:**
  - เพิ่ม **แผนภูมิแท่ง (Bar Chart)** หรือ **แผนภูมิวงกลม (Donut Chart)** แสดงสัดส่วนยอดขาย 5 อันดับแรก (Top 5 Best Selling Drinks) บริเวณด้านบนหรือด้านข้างของตารางสรุป เพื่อให้เจ้าของร้านมองเห็นสัดส่วนยอดขายและแนวโน้มความนิยมได้ในทันที

---

### 3. หลีกเลี่ยงข้อมูลเกินความจำเป็น (Avoid Information Overload / Minimalist Design)

- **การปฏิบัติตามหลักการ:** **ยังไม่ครบถ้วน / มีจุดบกพร่อง (Incomplete / Needs Improvement)**
- **การวิเคราะห์ชิ้นงานจริง:**
  - _จุดที่ผ่าน:_ รายงานตัดรายละเอียดธุรกรรมรายย่อย (Transaction-level details) ออกได้อย่างเหมาะสม ไม่แสดงประวัติใบเสร็จทุกใบ
  - _จุดที่ยังขาด:_ ในส่วนหัวของรายงาน (Header) ของกลุ่มเดิม มีการใส่ฟิลด์ **"พนักงาน: สมชาย"** ปรากฏอยู่บนหัวรายงานสรุปรายวัน ซึ่งในความเป็นจริงของร้านกาแฟ ใน 1 วันมีพนักงานผลัดเปลี่ยนเข้ากะหลายคน การใส่ชื่อพนักงานคนเดียวไว้บนหัวรายงานสรุปยอดรวมทั้งวันทำให้เกิดความสับสน เป็นข้อมูลที่ไม่ถูกต้องและเกินความจำเป็นสำหรับเจ้าของร้านที่ต้องการดูภาพรวมยอดขายของสาขา
- **ข้อเสนอแนะในการแก้ไขที่นำไปปฏิบัติได้จริง:**
  - ตัดฟิลด์ "พนักงาน" ออกจากส่วนหัวของรายงานสรุปยอดขายของร้าน
